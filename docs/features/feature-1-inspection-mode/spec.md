# Feature 1 — Inspection Mode / Element Picker — spec.md

## What it does

Lets the user toggle a click-to-select picker on any web page. While active, hovering highlights the element under the cursor; clicking locks selection to exactly one DOM node. This removes the ambiguity of describing a UI element in text ("the second child under the third div") by letting the user point instead — the core premise of SpotCheck.

**A "select the gap between two elements" mode was built, then deliberately removed.** A large share of real design-QA feedback is about the *space between* elements, not any one element — so a version of this feature let the cursor target that space directly, initially unconditionally, then gated behind holding Alt/Option after the unconditional version made certain wrapper containers unreachable by clicking inside them. Removed entirely after further feedback: the fix for spacing lives on the shared parent anyway (its `gap`/`display`, or its children's margins), so selecting that parent through plain, unmodified clicking — exactly what `getRelevantStyles` in Feature 2 already captures for any selected flex/grid container — gives the same actionable information without a second selection mode, a modifier key to learn, or `event.detail` needing to be polymorphic. One interaction, no exceptions, is worth more than a more precise but separate targeting mode. If gap-specific targeting is ever revisited, it should be designed as a deliberate power-user layer from the start, not something that can silently intercept a plain click.

## How it works

- **Injection is on-demand, not static.** The extension carries no `content_scripts` manifest entry; `background.js` injects the picker files via `chrome.scripting.executeScript` only when the user clicks the toolbar icon. Until that happens, the extension has zero footprint on any page.
- **Targeting uses `document.elementFromPoint(x, y)`**, which natively returns the innermost element at a given point — this is what gives DevTools-picker-style precision on nested/repeated component structures without any custom ancestor-walking logic. This is unconditional: whatever `elementFromPoint` returns is what gets selected, full stop — a wrapper, a leaf, a container with `gap`-spaced children, doesn't matter.
- **The highlight box lives in a Shadow DOM root**, attached to `document.documentElement`. This is a two-way isolation boundary: the host page's CSS can't leak in and distort the highlight box, and the highlight box's styles can't leak out and affect the page being inspected.
- **The box's position is re-synced every animation frame, not just when `showHighlight` is called.** `showHighlight` only fires from `picker.js`'s `mousemove`/`click` handlers — so scrolling the page without moving the mouse used to leave the box exactly where it last was, visually detached from the element it's meant to be tracking. Fixed with a continuous `requestAnimationFrame` loop, started once the shadow host exists and stopped on `teardown()`, that re-reads the last-highlighted element's live `getBoundingClientRect()` every frame regardless of what caused it to move — the same fix, for the same underlying reason, as Feature 3's persistent outlines (see that feature's `spec.md` for the fuller "why a `scroll` listener alone can't actually fix this" explanation). The CSS `transition` that used to ease the box between positions was removed at the same time — animating toward a fresh target every single frame during a scroll would look like the box trailing the element, the opposite of what tracking it is supposed to achieve; the eased motion only ever made sense for hopping between two different elements on hover, not continuous same-element tracking.
- **State is a single namespaced global** (`window.__spotcheck`), not ES modules — content scripts injected via `executeScript` in MV3 are simplest as classic (non-module) scripts sharing one isolated-world scope. Re-injection guards against re-declaring the namespace.
- **Selection handoff is event-based.** Locking an element dispatches `spotcheck:element-selected` on `document` with the element in `event.detail`. This is the *only* integration point other features use — Feature 1 has no knowledge of what happens after a selection is made.

## Guardrails specific to this feature

- **Permissions are `activeTab` + `scripting` only.** No `host_permissions`, no `<all_urls>`. The extension cannot act on a tab the user hasn't explicitly toggled it on for.
- **Off by default, fully torn down on toggle-off.** No listeners, no DOM nodes, no in-memory selection state should survive a toggle-off. This is verified explicitly in the plan.md test criteria, not just assumed.
- **Read-only capture.** The picker click handler calls `preventDefault()`/`stopPropagation()` purely to stop the *page's* click behavior (e.g. link navigation) from firing when the user is trying to select, not to modify the page. Nothing about the underlying page's DOM, styles, or state is altered — only the extension's own Shadow DOM overlay is added and later removed.
- **No persistent background activity.** Picker state is tracked in a simple in-memory `Map` in the service worker, not `chrome.storage`. Nothing needs to survive a browser restart for this feature, and not persisting it avoids the extension quietly holding onto stale per-tab state.

## Known limitations

- `elementFromPoint` cannot reach into cross-origin `<iframe>` content — the picker selects the iframe boundary itself in that case, not the element inside it. Documented as a v1 limitation, not fixed here.
- **No coordination with Chrome DevTools' own "Inspect Element" picker.** DevTools' native element picker runs in the browser's DevTools frontend, entirely outside any page's JS and outside the WebExtensions API surface — there is no documented API for a content script to detect or suppress it. The only thing that gets close is `chrome.debugger`, a heavyweight, security-sensitive permission that would break the minimal-permissions guardrail for a v1 scope boundary, not fix a bug. Practical guidance: don't run both pickers on the same page at once. Not fixed here, and not planned for v1.
- **No way to target the space between elements directly.** Feedback about spacing has to name the parent container (whose `display`/`gap` is already captured normally — see Feature 2) plus a description in the note of which children it's between. See the "select the gap" note above for why this was tried and removed rather than left as an opt-in mode.
- **Manually testing `event.detail` from the DevTools console needs the right execution context.** All content scripts (this feature and every one downstream) run in Chrome's *isolated world*, separate from the page's own *main world* even though both share the DOM. A freshly-typed console command runs in the main world by default. When a main-world listener observes a `CustomEvent` dispatched from the isolated world, Chrome structured-clones `detail` across that boundary — and a live DOM element reference (which `detail.element` always is, here and in Feature 2's `spotcheck:element-captured`) isn't structured-cloneable, so the whole `detail` comes back `null` to that listener even though the event fired correctly with real data. This is a console-testing artifact only — every real consumer (Feature 2, 3, 4) is itself a content script in the same isolated world as the dispatcher, so `detail` is never cloned for them. To verify `detail` manually from the console, switch the Console panel's context dropdown (top-left, defaults to "top") to the extension's content-script context before registering the listener, or temporarily `console.log` inside the dispatching content script itself.

## Relevance / dependencies

- **Feature 1 has no dependencies on other features.** It's the root of the pipeline — it can be built and fully tested in isolation with nothing downstream implemented yet.
- **Feature 2 (Capture Engine)** depends on this feature entirely: it listens for `spotcheck:element-selected` and, on that event, does its own work (selector path, computed styles, component name) against `event.detail.element`. Feature 1 does not call into Feature 2 directly — Feature 2 subscribes.
- **Feature 3 (Annotation Layer)** also listens for the same `spotcheck:element-selected` event to know when to open its popup/sidebar UI. Features 2 and 3 can both listen independently; Feature 1 doesn't need to know either exists.
- **Feature 4 (Export Bundle)** has no direct relationship to Feature 1 — it only ever touches the queued annotation data produced further down the pipeline.
