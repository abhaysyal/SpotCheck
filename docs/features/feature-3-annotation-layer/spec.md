# Feature 3 — Annotation Layer — spec.md

## What it does

Lets the user leave a free-text note on a locked element, right where they clicked — click locks the element and immediately opens a dark, anchored popup for typing a note; submitting collapses it into a small numbered bubble pinned to that element, Figma-comment-style, plus a persistent outline traced around it. Clicking a bubble later reopens it for editing or deleting. This is the v1-simplest version of the annotation layer: no preset tag categories, no separate review list — the bubbles (and outlines) scattered across the page *are* the queue.

**A parallel "gap annotation" path (for Feature 1's now-removed gap-selection mode) briefly existed alongside the element path documented below, then was removed with it.** Every store/positioning/render function here had a `kind` branch for a while; all of that is gone now — this file, and the code, are back to one target type: an element. See Feature 1's `spec.md` for why gap-selection was tried and dropped.

## How it works

- **Single click does two things at once: lock (Feature 1, unchanged) and open the note popup (this feature).** This was a deliberate interaction-model choice over a two-click "lock, then click again to annotate" flow — hover already gives a free preview, so click has always meant "I'm committing to this one" in Feature 1's model; folding annotation entry into that same click avoids inventing an in-between "locked but nothing's happening" state.
- **Numbers are earned by saving, not by looking.** Opening the popup and abandoning it without typing anything creates no record and consumes no number — only a successful, non-empty submit creates a bubble. This keeps the page from accumulating empty pins for elements the user merely glanced at.
- **One shared Shadow DOM host holds everything this feature renders** — an outlines layer, the bubbles layer, and the single reusable popup — same isolation rationale as Feature 1's highlight overlay (host-page CSS can't distort it, its own styles can't leak onto the page). Deliberately dark-themed (near-black background, light text) for the popup, a visual choice specific to this feature, not necessarily the rest of the extension.
- **A persistent outline is traced around every element with a saved annotation, and stays visible for as long as that annotation exists — not just while it's the "currently selected" one.** This is a deliberate departure from Feature 1's own highlight, which only ever shows one element at a time (whatever was most recently hovered/clicked). Added after early testing surfaced a real ambiguity: a small numbered bubble alone doesn't make it clear *which exact node*, especially a child nested inside a similarly-shaped parent, a given comment belongs to — the outline traces the actual boundary, and any number of them can be visible simultaneously. It's border-only, no fill, specifically because a translucent fill (like Feature 1's transient highlight uses) would visually compound wherever outlines overlap — which is the normal case for nested parent/child annotations, exactly the scenario this exists to disambiguate.
- **Hovering an already-annotated element adds the same green fill Feature 1's locked highlight uses, but only for the duration of the hover.** The border itself already stays permanently once annotated (the point of the bullet above) — this is purely the transient fill on top, there to reinforce "this already has feedback" as the cursor passes over it, the same way it would if you were about to lock it fresh. Same `rgba(34, 197, 94, 0.08)` value as `.box.locked` in `overlay.js`, not an approximation. Tracked with an independent `mousemove` listener (own `elementFromPoint` hit-test against `annotationsByElement`, not a read of `spotcheck.state.hoveredElement` — same "don't reach into Feature 1's internals" reasoning as everywhere else in this file), registered/removed alongside the `scroll`/`resize` listeners in `start()`/`stop()`.
- **Storage is a `WeakMap<Element, AnnotationRecord>` plus a parallel ordered array.** Keying directly on the live element reference (the same one Feature 1 hands off and Feature 2 captures against) avoids inventing a synthetic id, and lets entries become garbage-collectable naturally once an element is genuinely gone rather than needing manual cleanup. The ordered array exists purely because a `WeakMap` isn't iterable and Feature 4's export needs a stable, ordered walk of every annotation.
- **A second, separate `WeakMap` (`latestCaptureByElement`) caches the most recent capture for *any* selected element, independent of whether it's annotated.** This exists to fix a real bug, found during Feature 4's live end-to-end verification, not a design taken on faith: `spotcheck:element-captured` fires immediately on selection, but an annotation record isn't created until *commit* — typing a note and clicking send, a separate and later user action, not "the same click" the original design assumed. A listener that only writes onto an already-existing record finds nothing there for a brand-new annotation and silently drops the capture, shipping every first-time annotation with `selector`/`styles`/`component` all `null`. The fix: the capture listener always populates this cache regardless of whether an annotation exists yet, and `saveNote` reads from it once, at record-creation time, rather than waiting on a second capture event for that element that was never going to arrive. Re-selecting an *already-annotated* element (e.g. via its bubble, to edit it) still gets refreshed directly too, since that path doesn't go through `saveNote`'s cache read again.
- **New events: `spotcheck:annotation-saved`** (every successful save, new or edited, carrying `{ number, note, selector, element }`) **and `spotcheck:annotation-deleted`** (every delete, carrying `{ number, element }`). Both are hand-off points a future Feature 4 will consume to keep its own view of the queue in sync — neither is otherwise used within this feature itself.
- **Deleting renumbers everything after it, so the visible sequence never has gaps.** A record's `number` is derived from its live position in `annotationsInOrder`, not assigned once and kept forever — deleting #2 out of #1/#2/#3 immediately relabels the old #3 as #2. This is a deliberate tradeoff: numbers describe "current position in the queue," not a permanent identity. Made cheap and safe by carrying the bubble's DOM node directly on its record (`record.bubbleEl`) rather than in a separate number-keyed map — a map keyed by number would itself go stale the instant a number shifts.
- **The delete icon doubles as cancel for an unsaved draft.** There's no separate "cancel" affordance — clicking delete on a popup that was never saved (no existing record for that element yet) just discards the draft and closes, the same outcome as clicking delete on a saved one minus the actual record removal. One control, context-dependent effect, rather than two similar-looking buttons.
- **Both popup buttons are icon-only** — an up arrow (↑) for send, a trash icon (🗑) for delete — no visible text labels. `aria-label`s cover accessibility; this is a deliberate compact-UI choice, not an oversight to "add labels later."
- **Tracks its own on/off lifecycle independently of `picker.js`.** Registers its own `chrome.runtime.onMessage` listener for the same `SPOTCHECK_SET_ACTIVE` broadcast rather than reading `picker.js`'s internal `active` flag — keeps this feature decoupled from Feature 1's internals (per the cross-feature convention in `CLAUDE.md`) while still starting/stopping correctly alongside inspection mode. That broadcast is an *absolute* state (`{ active: boolean }`), not a flip — it started as a flip-only message, but with this feature adding a second independently-toggling listener, a flip protocol let transient desync between listeners compound instead of self-correct (surfaced as an intermittent "needs two clicks" toggle bug). See Feature 1's `spec.md`/`plan.md` for the fuller rationale.
- **Clicking a bubble reuses the exact same selection path a fresh page click does.** Its handler calls `spotcheck.setSelectedElement(record.element)`, not `openPopupFor` directly — this is what makes clicking a bubble show the same green locked highlight a fresh element click shows (that call moved into `setSelectedElement` itself, in `state.js`, specifically so both paths converge instead of duplicating the highlight call at each site).
- **Bubbles are de-overlapped as a group, not positioned independently.** Nested parent/child elements very often share the same (or a near-identical) top-left corner — a full-bleed child with no padding inside its parent, for instance — which would otherwise stack their bubbles exactly on top of each other: visually indistinguishable, and whichever ends up underneath becomes unclickable. `positionAllBubbles()` processes every annotation in creation order (which also matches numbering), and a bubble that collides with an already-placed one cascades to the nearest free spot instead. Earlier annotations keep their ideal corner-anchored position; later, colliding ones cascade away from it — a stable, deterministic rule, not an arbitrary one.
- **Bubble positions are clamped to the viewport; outline positions are not.** The bubble is a small fixed-size clickable marker, so it's clamped the same way the popup already is — an annotated element near the top/left edge (a sticky header, for instance) would otherwise push its pin to a negative coordinate and off-screen entirely. The outline exists to trace the element's *real* position, including partially or fully off-screen, so clamping it would defeat its purpose.
- **Outline/bubble/popup positions are recomputed from live `getBoundingClientRect()` calls inside a continuous `requestAnimationFrame` loop, not in response to `scroll`/`resize` events.** An earlier version used `scroll`/`resize` listeners with `passive: true` and treated the residual lag as an accepted tradeoff — that was wrong to settle for, not just imprecise: the browser paints a new scroll offset on its own compositor thread before a `scroll` event even reaches a content script's main-thread listener, so *anything* triggered by that event is structurally at least one step behind what's already on screen, regardless of how the listener itself is tuned. A loop that just re-reads live rects every single animation frame, independent of what caused something to move, doesn't have that gap — verified directly: after a real (not synthetic-event) scroll, an outline's position matches its element's `getBoundingClientRect()` to the pixel, with zero scroll listeners registered anywhere. The tradeoff is a small constant amount of work every frame while inspection mode is on, even completely idle — accepted given the realistic number of annotations this extension deals with (tens, not thousands). Feature 1's own transient highlight box (`overlay.js`) had the identical gap and got the identical fix — see that feature's `spec.md`.
- **The popup anchors to the bubble's actual rendered position when reopening an existing annotation, never to the element's own rect.** This was a real bug, not a stylistic choice: `positionAllBubbles` cascades a bubble away from its "ideal" corner-anchored spot whenever it would otherwise overlap another bubble, so the bubble and the element's own rect can genuinely disagree about where "here" is — reported as the popup opening "in the wrong place" and, since it could visually land near or on top of an unrelated bubble, looking like several bubbles were reacting to one click. `getPopupAnchorRect(el, record)` resolves this: `record.bubbleEl.getBoundingClientRect()` when a bubble already exists (the normal case — clicking the bubble itself, or clicking the underlying element directly, both resolve to the same existing record and the same bubble-anchored position), falling back to the element's own rect only for a brand-new draft that has no bubble yet to anchor to. `openPopupFor` also forces a `positionAllBubbles()` pass before computing the anchor, so the bubble position it reads is never stale even if the click happens between reposition frames. Verified directly against a live three-annotation cascade: reopening any of them puts the popup at exactly `bubble.left`, `bubble.bottom + 8`, to the pixel, regardless of how far the cascade had pushed that particular bubble.
- **One necessary touch to `picker.js`'s click handling.** `picker.js`'s click listener is a `document`-level capture-phase interceptor by design (that's how it hijacks page clicks into element-selection); left unmodified, it would swallow every click on this feature's own bubbles before they ever reach this feature's listeners, since capture-phase listeners on `document` fire before the event reaches anything inside a nested Shadow DOM tree. The fix is a single early-return: if `document.elementFromPoint` at the click coordinates resolves to this feature's own shadow host (which is what it returns for any point covered by a Shadow DOM tree, since shadow trees are encapsulated from outside DOM queries), `picker.js` skips its own lock logic entirely — no `preventDefault`/`stopPropagation` — so the click continues on to this feature's own listeners normally. This is plumbing to make cross-feature clicking work, not feature-logic coupling: `picker.js` doesn't know or care *what* is inside that host, only that it isn't page content.

## Guardrails specific to this feature

- **Still no new permissions, still no network calls.** Rendering the popup/bubbles, tracking positions, and storing notes are all pure DOM/JS operations within the already-injected content script — `manifest.json` stays at `["activeTab", "scripting"]`.
- **Still nothing written to the page being inspected.** Every DOM node this feature creates lives inside its own Shadow DOM host, appended once to `document.documentElement` — nothing is added to, or modified on, the host page's own markup, styles, or elements.
- **In-memory only, resets on toggle-off — true as originally shipped, superseded by Feature 6.** At the time this feature was built, this was consistent with the rest of the extension's "nothing persists, no `chrome.storage`" stance. **As of Feature 6, this is no longer accurate**: the queue is durably persisted via `chrome.storage.local` (a new `storage` permission, confirmed with the human reviewer — see `docs/features/feature-6-annotation-capture-edit/spec.md`'s "Storage decision"). What's still true: the on-page *visual* state (bubbles, outlines) is still DOM-bound and still resets on toggle-off; only the underlying data survives.
- **Empty/whitespace-only notes are never persisted — true as originally shipped, since removed.** `saveNote()`'s empty-note guard was a real bug once the mandatory-fields model changed in Feature 5/6 (an issue-type-only submission with no note is now valid, and this guard was silently eating it) — it was removed entirely during Feature 5/6 hardening. The current gate is Issue-type-selected, full stop; see Feature 5's spec.md "Current Issue type model."

## Known limitations

- **Escape can still discard an unsaved draft.** `picker.js`'s existing Escape handler (Feature 1) clears the current lock unconditionally, including while keyboard focus is inside this feature's note textarea — pressing Escape out of habit while typing (e.g. to dismiss a browser autofill dropdown) loses whatever hadn't been submitted yet. This is a known, explicitly deferred gap (project decision, not an oversight) — a fix would need `picker.js`'s Escape handler to check whether focus is currently inside a text input/textarea anywhere on the page, including inside an open shadow root, and skip clearing if so. Left as a `// TODO`, not solved in this pass.
- **No preset tag categories — true as originally shipped, since built in a different shape.** The original design called for a preset tag (spacing/color/wrong-token/broken-interaction/other) alongside the note; v1 shipped free-text only, with preset tags tracked as a Phase 2 roadmap item in `PROJECT.md` §8. **v2's Feature 5 built this**, per an actual Figma design rather than the guessed category list above: a grouped, single-select Issue-type dropdown (Property: Color/Typography/Spacing/Layout; Structure: Component/Component Variant/State-Interaction/Other). See that feature's spec.md.
- **An annotated element that's later removed from the DOM** (SPA re-render, navigation within the page) leaves its bubble *and* outline hidden with no recovery/reassignment path in v1 — the annotation data still exists in memory, just nothing to visually anchor it to anymore.
- **No confirmation before abandoning an unsaved draft.** Clicking a different element while a popup has unsaved text silently discards that text — consistent with how Feature 1 already treats every click as an immediate commitment, but worth knowing about, especially combined with the Escape gap above.

## Relevance / dependencies

- **Depends on Feature 1** for `spotcheck:element-selected` (drives when to open the popup) and requires the Step 5 change to `picker.js` to receive clicks on its own bubbles at all.
- **Depends on Feature 2** for `spotcheck:element-captured` to fill in `selector`/`styles`/`component`. **Correction to an earlier version of this note**: capture *does* arrive synchronously right after selection, but a record doesn't necessarily exist yet when it does — commit (typing a note, clicking send) is a separate, later user action, not the same click as selection. See the `latestCaptureByElement` cache above, in "How it works," for how this feature actually bridges that gap; it's not a non-issue that can be ignored.
- **Feature 4 (Export Bundle)** is the intended consumer of everything this feature produces: it needs to walk `annotationsInOrder` (or listen for `spotcheck:annotation-saved`/`spotcheck:annotation-deleted` and build its own list) to serialize the full queue — number, note, selector, and whatever Feature 2 data is attached — into the final clipboard export. This feature has no awareness of Feature 4 beyond dispatching those two events; it doesn't know or care whether anything is listening. Worth Feature 4 knowing up front: numbers are positional (see "How it works" above), so if it ever caches a number anywhere instead of reading `annotationsInOrder` fresh at export time, a delete that happens in between would make that cached number wrong.
