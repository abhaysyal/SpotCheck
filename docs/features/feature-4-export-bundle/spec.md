# Feature 4 — Export Bundle — spec.md

## What it does

Serializes the entire current annotation queue into one Markdown document and copies it to the clipboard — a small floating button, shown only once at least one annotation exists, is the only UI. This is what makes the rest of the pipeline (Feature 1 locks an element, Feature 2 captures its data, Feature 3 attaches a note) actually useful: without an export step, everything gathered so far never leaves the browser tab.

## How it works

- **Markdown, not JSON — a deliberate choice, not a placeholder for "add JSON later."** The described workflow end-to-end is "copy, paste into a chat with Claude Code / ChatGPT / Cursor." Markdown is what reads as a report in that context — headers, bold labels, inline code for selectors, a fenced `css` block for styles. JSON would be equally parseable by the model reading it, but reads as *data* rather than as the human-authored-feeling bug report the note text is meant to be. If a machine-consuming path (the Phase 2 local MCP server in `PROJECT.md` §8) is ever built, that's its own design problem — not a second output mode bolted onto this button.
- **One button, one action, the whole current queue.** No selection UI, no preview step, no partial export. Click → clipboard has everything.
- **The button is invisible until there's something to export.** Zero annotations means zero UI footprint from this feature — consistent with the rest of the extension's "inert until there's a reason to show something" posture.
- **Feature 3 had to change to make this possible without breaking the event-only convention.** Two things:
  1. Its records now also carry `styles` and `component` (previously only `selector` was stored, since nothing needed the rest before this feature existed) — filled in from the same `spotcheck:element-captured` listener that already fills in `selector`.
  2. `spotcheck:annotation-saved` and `spotcheck:annotation-deleted` now both carry an `allAnnotations` field — the complete, freshly-rebuilt ordered list, not just the one record that changed. This exists specifically because annotation numbers are positional (deleting #2 renumbers #3 down to #2, documented as a known behavior in Feature 3's own `spec.md`) and Feature 3 never dispatched a change event for the *other* records a delete implicitly renumbers. A consumer caching per-item data from the old, single-record events would show a stale number for anything after the deleted item. This feature never patches its local list incrementally — every event fully replaces `annotations` with `detail.allAnnotations` — so that entire class of staleness bug can't happen on this side, regardless of what changes upstream.
- **A shared `spotcheck.uiHosts` registry (a `Set`, initialized once in `state.js`) replaces the one-off host-equality check `picker.js` used to have for Feature 3 alone.** `picker.js`'s click/hover handling needs to step aside for clicks landing on *any* of SpotCheck's own Shadow DOM UI — previously that meant one hardcoded `hitEl === spotcheck.annotations.hostEl` check; adding this feature's own export-button host would have meant a second hardcoded branch, and a third feature after that a third. Instead, every feature's `ensureHost()` adds its host to the shared set, `stop()` removes it, and `picker.js` just checks membership. `picker.js` still doesn't know *what* Feature 3 or this feature actually are — only that clicking inside their UI isn't a page-element selection.
- **The button is created eagerly on `start()`, not lazily on first use like Feature 3's popup.** Feature 3's `ensureHost()` is lazy because there are several different conditional paths that might need the popup first. This feature has exactly one trigger (its own click) and one job, so creating its host once when inspection mode turns on — then toggling visibility via CSS based on the live annotation count — is simpler than replicating Feature 3's lazy-creation bookkeeping for no real benefit.
- **Computed style property names are converted from camelCase to kebab-case before being written into the fenced `css` block.** `getComputedStyle` (Feature 2) returns JS property names like `backgroundColor`; real CSS reads `background-color`. Presenting the JS-cased version in a block explicitly labeled ` ```css ` would look wrong to both a human skimming it and a model expected to reason about it as actual CSS.
- **The "Copied" confirmation re-derives its label from the current count when it reverts, rather than restoring whatever the button said a moment before.** If another annotation was saved or deleted during the ~1.5s the confirmation is showing, reverting to a stale count would be a small but real correctness gap in a feature whose whole point is "give me an accurate snapshot."

## Guardrails specific to this feature

- **Still clipboard-only, still no network calls.** `navigator.clipboard.writeText()` is the only way data leaves the page — no `fetch`, no download, no background sync. This is the literal guardrail `PROJECT.md` §6 states for this feature by name ("v1: clipboard only — no server, no network call, nothing running in the background").
- **Still no new permissions.** `navigator.clipboard.writeText()` from a content script works from a genuine user-click handler without any manifest permission addition — `activeTab` + `scripting` remains the complete permission set for the whole extension, all four features.
- **Nothing written to the page being inspected.** This feature's only DOM footprint is its own Shadow DOM button, added once and removed on toggle-off — same isolation model as every other feature's UI.
- **In-memory only, resets on toggle-off.** This feature's local `annotations` array (and the button itself) are discarded entirely when inspection mode turns off, consistent with the rest of the extension — there was never a point at which this feature's own state needed to outlive that toggle.

## Known limitations

- **No format choice — Markdown only.** Deliberate, see "How it works" above, not an oversight to revisit casually.
- **No partial/selective export.** Every annotation currently queued goes into the bundle every time; excluding one means deleting it first (Feature 3), not deselecting it here.
- **Clipboard-write failures are logged, not surfaced to the user.** `navigator.clipboard.writeText()` can reject in edge cases (page lost focus at the exact moment of the click, an unusual permissions-policy configuration) — caught and `console.warn`'d, not turned into a visible error state. Acceptable for v1 unless this turns out to be a real, recurring occurrence rather than a theoretical one.
- **The button's fixed bottom-right position doesn't account for other fixed-position UI the page itself might already have there** (a chat widget, a "back to top" button). Same category of tradeoff every other fixed-position piece of this extension's UI already accepts.

## Relevance / dependencies

- **Depends on Feature 3** for `spotcheck:annotation-saved`/`spotcheck:annotation-deleted`, specifically their `allAnnotations` field — this feature never reads Feature 3's internal `annotationsInOrder` array directly, and never listens to Feature 1/2's events itself. Everything it needs arrives already assembled.
- **Depends indirectly on Feature 2** only in the sense that `styles`/`component` on each exported annotation are whatever Feature 2 captured — if a capture is still `null` (e.g. the `spotcheck:element-captured` event for that particular click hasn't landed yet, in principle possible though not observed in practice since they fire synchronously back-to-back), the corresponding line is simply omitted from that annotation's Markdown section rather than showing a placeholder.
- **Nothing depends on this feature.** It's the terminal stage of the pipeline — Feature 1 locks, Feature 2 captures, Feature 3 annotates, this feature is where the data leaves the browser. Nothing downstream exists in v1.
- **The `spotcheck.uiHosts` registry, introduced by this feature, is now a piece of shared infrastructure any future feature with its own clickable Shadow DOM UI should use** — register on `ensureHost()`, unregister on `stop()` — rather than `picker.js` growing another hardcoded host-equality branch per feature.
