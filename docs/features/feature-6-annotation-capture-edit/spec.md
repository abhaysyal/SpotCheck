# Feature 6 — Annotation Capture & Edit — spec.md

## What it does

Wires Feature 5's popup shell to real behavior: tag-scoped computed-CSS capture keyed off the chosen Issue type, real on-demand screenshot capture, debounced hot-save for editing an existing annotation (replacing Feature 5's edit-mode send button with a saved-confirmation indicator), automatic reopening of a previously agent-resolved/verified annotation when it's edited again, and a durable, swappable local data layer for the annotation queue — the same store Feature 7's local MCP server will read from directly, built now so Feature 7 doesn't have to retrofit persistence into a feature that never had it.

## Storage decision — confirmed with the human reviewer before writing this plan

The written brief's "local persistence... the same storage Feature 7 will later expose over MCP" only makes sense as **durable, cross-process-readable storage** — a future standalone MCP server process cannot reach into a content script's in-memory `WeakMap` at all. That requires `chrome.storage.local`, a new `"storage"` permission, and a real, visible reversal of `CHROMEWEBSTORE.md`'s current "No storage — nothing persists across sessions" language. This was flagged explicitly and confirmed before implementation, per `CLAUDE.md`'s own instruction to stop and flag rather than implement around a stated guardrail — **confirmed: proceed with `chrome.storage.local`**, updating the manifest and `CHROMEWEBSTORE.md` to match reality rather than leaving them stale.

**What this does *not* mean**: the queue persisting durably does not mean the on-page visual state (bubbles, outlines) does. Those live only as long as the content script instance that drew them. This feature explicitly does **not** rehydrate bubbles/outlines from storage when inspection mode is toggled back on — the persisted queue and the live, DOM-bound rendering state are two different things now, and only the data layer survives a toggle-off. Re-drawing annotations from storage on re-toggle (re-resolving each stored `selector` against the current page, handling ones that no longer resolve) is a real, separate problem — left as an explicit known gap for a later feature, not solved or silently ignored here.

## How it works

### Tag-scoped computed CSS capture

- **Recomputed fresh at the moment of every save (explicit send, or a hot-save), never cached from when the Issue type was first picked.** The written brief's property groups per Issue type are implemented as the closest reliable computed-style equivalent, not literal shorthand property reads:
  - **Color** → `color`, `backgroundColor`, `borderColor`
  - **Typography** → `fontFamily`, `fontSize`, `fontWeight`, `lineHeight`, `letterSpacing`
  - **Spacing** → the four longhand margin/padding properties (`marginTop/Right/Bottom/Left`, `paddingTop/Right/Bottom/Left`), `gap`, `width`, `height` — `getComputedStyle` resolves individual longhands reliably; a literal `margin`/`padding` shorthand read doesn't always resolve consistently when the four sides differ, and Feature 2 already established the longhand convention for this exact reason (see `capture.js`'s `BASE_PROPERTIES`).
  - **Layout** → `display`, `position`, `top`, `right`, `bottom`, `left`, `zIndex`, plus Feature 2's own `FLEX_PROPERTIES`/`GRID_PROPERTIES` conditionally, mirroring (not importing) Feature 2's exact lists — `capture.js`'s consts are private to its own closure, and duplicating two five-item arrays with a comment pointing at the original is a smaller footprint than exporting new surface from an already-shipped, tested feature file. If Feature 2's lists ever change, this needs updating too; noted at the duplication site.
  - **Other** → every computed property actually enumerable on the element (`for (let i = 0; i < computed.length; i++)`), not a curated subset. Deliberately keyed by the browser's own kebab-case property names here (`background-color`, not `backgroundColor`) — this is the one path that isn't curated, so it doesn't pretend to share a shape with the curated ones.
- **Stored on the record as `tagScopedStyles`, a new field, separate from Feature 2's existing `styles`.** Feature 2's original selection-time snapshot (`styles`) is untouched and still populated exactly as before — this feature adds a second, Issue-type-aware snapshot rather than replacing the first. `capture.js` itself is not modified.

### Real snapshot capture

- **Captured once, at the moment `includeSnapshot` is checked — not deferred to send time, and not re-captured on every hot-save.** This revises Feature 5's spec, which described capture happening "at send time"; that framing assumed a send button always exists. Once edit mode has no explicit send action (see below), "send time" isn't a moment that exists to hang capture off of, and re-capturing on every debounced hot-save while someone is mid-typing would mean hiding/showing the popup — visibly flickering — several times a minute. Checking the box is already a deliberate, discrete action; that's the new trigger, for both add and edit mode alike, so there's one rule instead of two.
- **Mechanics**: content scripts can't call `chrome.tabs.captureVisibleTab` directly — only extension pages (background, popup) can. `toggleSnapshotCheckbox` sends a `SPOTCHECK_CAPTURE_VISIBLE_TAB` message; `background.js` calls `chrome.tabs.captureVisibleTab(windowId, { format: "png" })` and replies with the data URL or an error. The content script then: hides the popup, waits one animation frame (a style change needs a paint to actually be absent from the next captured frame), requests the capture, restores the popup, and crops the result to the element's bounding box on an offscreen `<canvas>` — scaled by `window.devicePixelRatio`, since `captureVisibleTab` captures at device pixels while `getBoundingClientRect()` reports CSS pixels.
- **Fails silently, exactly as Feature 5's spec already committed to**: any failure (an expired `activeTab` grant, hitting `captureVisibleTab`'s own per-second rate limit, a cropped region computing to zero size) is caught, logged with `console.warn`, and leaves `includeSnapshot` checked with `snapshot` staying `null` — the rest of the annotation is entirely unaffected.
- **Unchecking and rechecking re-captures.** The stored image isn't kept around once its checkbox is off; toggling back on takes a fresh one rather than restoring a stale cached one.

### Hot-save (edit mode only)

- **Add mode is unchanged from Feature 5**: still an explicit send button, still gated on Issue type being selected (post-Feature-5-merge, that's the entire gate — no chip/note requirement layered on top), still creates the record only on a successful click.
- **Edit mode's send button is removed, per Feature 5's own `// TODO` and written spec** — replaced by a small "✓ Saved" indicator in the same footer slot, shown briefly (1.5s, matching the existing pattern `export.js`'s "✓ Copied" already established) after a debounced autosave actually writes. Delete's edit-mode-only visibility is unchanged.
- **Debounced 500ms after the last change**, triggered by: selecting a different Issue type, toggling the snapshot checkbox, or typing in the note — the same set of interactions that update `draftState` in add mode, just routed to a save instead of sitting inert until a button click that no longer exists. (Originally also included "toggling any cause chip" — chips were removed in Feature 5's post-approval dropdown merge, see that feature's spec.md.)
- **Respects the same mandatory-fields gate as add mode.** If an edit brings the record below the minimum (Issue type cleared back to unselected — the only way this can happen now that chips are gone), the debounced save is skipped — nothing is written, no "Saved" indicator appears, and the record keeps whatever its last valid state was until the gate is satisfied again. This isn't stated explicitly in the written brief, but the alternative — silently persisting an annotation that no longer meets the extension's own minimum bar — seemed like the wrong default; flagging it here as a judgment call, not an explicit instruction.

### Auto-reopen on edit

- Every record gains `status` (`"open" | "agent-resolved" | "verified"`, default `"open"`), `resolutionSummary` (`string | null`, default `null`), and `history` (`string[]`, append-only). Nothing in this feature ever sets `status` to anything but `"open"` or writes a `resolutionSummary` — those are Feature 7's future resolve-tool's job. This feature only needs to correctly *undo* them.
- **Any successful save (hot-save or, in principle, a fresh add-mode send, though a fresh annotation is never anything but `"open"` already) checks `status` first.** If it isn't `"open"`, the save pushes `` `previously resolved: ${resolutionSummary}, reopened after edit` `` onto `history`, clears `resolutionSummary` back to `null`, and resets `status` to `"open"` — all in the same write, before anything else about the edit is applied. This lives in the same shared apply step both `commit()` and hot-save call through, so there's exactly one place this rule is implemented, not two.

### The data layer (`content/queue.js`, new file)

- **One new content script, self-contained, no dependency on `annotations.js`'s internals** — same pattern every other feature file already follows. Exposes `spotcheck.queue = { upsert(record), remove(id), getAll(), clear() }`, all `async`, backed by a single `chrome.storage.local` key holding a plain array of serializable records.
- **Every record gets a stable `id` (`crypto.randomUUID()`), generated once at creation.** The existing `WeakMap<Element, Record>` store stays exactly as it is — it's what the positioning loop, hover-fill, and bubble-click-to-reopen logic all need a *live* element reference for, and none of that changes. The queue is a parallel, serializable mirror of the same data, keyed by `id` instead of a DOM node, with `element`/`bubbleEl`/`outlineEl` stripped before anything is handed to `queue.upsert()` — those three fields can't survive `JSON`-shaped storage and nothing outside the live content script instance needs them.
- **`stop()` (toggle-off) no longer clears the queue.** It still resets everything it always reset — the in-memory `WeakMap`/array, all bubble/outline DOM nodes, `draftState` — none of that can meaningfully survive a toggle-off regardless of storage (the DOM nodes are gone, and a fresh toggle-on re-injects a brand-new content script instance with fresh closures). What changes is that the *persisted* copy in `chrome.storage.local` is left alone, specifically so it survives past this feature's own lifetime the way Feature 7 needs it to.

## Guardrails specific to this feature

- **New permission: `storage`.** Confirmed with the human reviewer (see above) as a deliberate, visible policy change — not a quiet workaround. `manifest.json` and `CHROMEWEBSTORE.md` both updated in this pass; `CHROMEWEBSTORE.md`'s existing "No storage" language is corrected, not left contradicting the code.
- **`chrome.tabs.captureVisibleTab` needs no new permission** — it's covered by the `activeTab` permission already granted, but it can only be called from `background.js`, not a content script, which is why this feature is the first one since Feature 1 to touch `background.js` again.
- **Still no network calls from this feature itself.** Screenshot data stays local (cropped in-page via `<canvas>`, stored in `chrome.storage.local`); nothing this feature writes is uploaded anywhere. (As of Feature 7, the queue this feature persists is pushed by `background.js` to a local companion MCP server — see `docs/features/feature-7-local-mcp-server/spec.md` — but that push is Feature 7's own code, not anything added here.)
- **`capture.js` is not modified.** Its existing selection-time `styles` capture, its guardrails, and its known limitations all carry over unchanged; this feature only adds a second, separate capture path alongside it.

## Known limitations

- **No rehydration from storage on re-toggle**, as detailed above — an explicit, deliberate scope cut for this feature, not an oversight. A previously-recorded annotation's data survives in `chrome.storage.local`; its bubble/outline do not reappear on the page until a future feature re-resolves stored selectors against the live DOM.
- **`export.js` (Feature 4) is not touched.** Its Markdown output still reflects only what it already knew how to format (note, selector, Feature 2's `styles`, `component`) — it has no awareness yet of `issueType`, `causes`, `tagScopedStyles`, or `snapshot`. Extending the export format to actually use this feature's new data is a real, visible gap, left for whichever feature is scoped to touch export next.
- **`chrome.storage.local`'s default quota (10MB, no `unlimitedStorage` permission requested)** could plausibly be hit by a long session with many snapshot-heavy annotations. Not mitigated in this pass (e.g. no image downscaling beyond the natural crop-to-element-size) — cropping to a UI element's own bounding box keeps individual images small in the overwhelmingly common case, but this isn't a hard guarantee for a very large annotated element.
- **A hot-save that fails the mandatory-fields gate leaves the record's last valid state in place with no user-visible explanation** (see "Hot-save," above) — same category of gap as Feature 5's "no visible feedback for a disabled send button beyond dimming."

## Relevance / dependencies

- **Depends on Feature 5** for `draftState`, the mandatory-fields gate (`updateSendEnabled`), and every DOM element (`issueTypeTrigger`, the checkbox, `sendButton`/`deleteButton`) this feature adds behavior to or hides. (Feature 5's separate cause chips existed at the time this feature was built and are referenced above for that reason; they were later merged away — see Feature 5's spec.md — before this feature's own logic needed updating for it, since this feature's gate/hot-save already keyed off `issueType` as the primary field.)
- **Depends on Feature 2** for the selection-time `styles`/`component`/`selector` capture this feature's own tag-scoped capture sits alongside, and for the `FLEX_PROPERTIES`/`GRID_PROPERTIES` lists this feature mirrors for the Layout Issue type.
- **Feature 7 (Local MCP Server) is the intended consumer of `spotcheck.queue`.** Every field this feature adds to a record (`id`, `tagScopedStyles`, `snapshot`, `status`, `resolutionSummary`, `history`) is exactly what Feature 7's read-only tools need to expose. Feature 7 should not need to touch this feature's capture/hot-save logic — only read from `chrome.storage.local` under the same key `queue.js` writes to.
- **No dependency on Feature 8.** Component-name detection already flows through from Feature 2 unchanged; this feature doesn't add to or rely on it.
